## 0. 記法

本文の記述は次の 4 種類に分ける。無印が確定事項であり、実装はこれに従う。

| 印 | 意味 |
|---|---|
| 無印 | 確定。作成者が決めた事項、初版から維持する事項、または確定事項から直接導かれる帰結（その旨を添える） |
| 【提案】 | 確定事項を満たすための技術案。作成者は未承認。実装前に採否を決める |
| 【未決】 | 作成者の判断待ち。決まるまで実装の前提にしない |
| 【未検証】 | 外部サービスの挙動を実機で確認していない。実装時または受入試験で確認する |

【提案】【未決】【未検証】はすべて 12 章「実装前確認一覧」のいずれかの項目に対応する。本文中で質問を増やさず、12 章で一括して扱う。

## 1. 目的

自分が過去に書いた Zenn 記事 1 本を教師データとし、同じ文体・構成で、対象プロジェクト全体を解説する記事を書ける「生成環境」を自動反復で作り上げる。

チューニング対象はモデルの重みではなく、生成 AI に渡す環境（system prompt、スタイルガイド、ツール設定）である。記事は毎 iter ゼロから生成し直し、修正は環境側にのみ加える。

教師記事と生成記事は同じプロジェクトを扱う。教師記事は Zenn に公開済みで、その内容の情報源は対象プロジェクトの GitHub リポジトリである。掲載場所（Zenn）と情報源（GitHub）は区別して扱う。

## 2. 用語

| 用語 | 意味 |
|---|---|
| 教師記事 | 自分が執筆した Zenn 記事。1 本のみ。公開済み |
| 対象プロジェクト | 教師記事が解説している自分の public GitHub リポジトリ。generator が情報源として読む唯一のリポジトリ |
| 題材 | generator に与える「何について書くか」の指示。本基盤では「対象プロジェクト全体の解説」に固定する |
| 環境 | generator に渡す system prompt、スタイルガイド、ツール設定の束。git で版管理する |
| ルーブリック | 採点軸ごとに 0〜4 点の状態を文章で定義した採点表 |
| run | 環境のチューニング 1 サイクル。合格または反復上限で終了する |
| iter | run 内の 1 反復。生成、採点、環境修正の 1 周。1 iter で生成する記事は 1 本 |
| 教師記事 URL 集合 | 教師記事を指す URL とその自明な変種の集まり。8.1.2 で定義する。web 検索の除外とツール層のマスクの対象 |
| Grok Bot 専用通知経路 | 作成者が本基盤専用に用意する Grok Bot 専用 webhook。基盤からは一方向に POST する。Grok Bot 側でこの webhook を提供する仕組みの名称（routine、webhook trigger 等）は本書で断定せず、12 章 C-2 で確認する |

## 3. スコープ

### 3.1 含む

- 教師記事からのルーブリック抽出と作成者レビュー
- 対象プロジェクト全体解説記事の生成、採点、環境修正の自動ループ（1 run あたり最大 20 iter）
- run の終了（合格、20 iter 未達）の作成者への通知
- ループ全体の定期監視と、検知した異常の `jobs/` 配下への記録（7.6）
- 全サービスを 1 リポジトリに収め、Docker で分離して実行

### 3.2 含まない

- モデルのファインチューニング
- Zenn への自動投稿
- 複数ユーザーへの対応
- 合格した環境の別題材での汎用性評価（初版 3.1 の該当行、6.3、env_evaluator は廃止）
- 複数 run を束ねる上限や、run をまたぐ題材の切り替え
- Issue や ADR ごとの個別記事の生成。Issue、ADR、ドキュメントは調査資料であり、題材ではない
- xAI API（Grok モデルの API 利用）。通知は Grok Bot 専用通知経路で行う（7.5）。通知文の生成に LLM を使わないことは【提案】（7.5、12 章 B-5）

## 4. 前提条件（確定）

| 項目 | 確定内容 |
|---|---|
| 教師記事 | 1 本。作成者自身の Zenn 公開記事 |
| 教師記事の題材 | 対象プロジェクト（自分の public GitHub リポジトリ）そのものの解説 |
| 生成する記事 | 対象プロジェクト全体を解説する記事 1 本。毎 iter ゼロから生成し、前 iter の記事は入力にしない |
| 題材指示 | 「対象プロジェクト全体の解説記事を書く」の一文。参照資料の一覧は作成者が入力しない。何を読むかは generator が環境に従って決める |
| 情報源 | 対象リポジトリのみ。Issue、ドキュメント、ADR が整備されている |
| 情報源へのアクセス | 外部 API サーバーは作らない。generator から GitHub REST API を直接読む |
| web 検索 | generator に許可する。ただし教師記事 URL 集合を除外する（8.1） |
| 合格基準 | ルーブリック合計の 80% 以上。ほかの合格条件は設けない |
| 反復上限 | 1 run あたり 20 iter。合格した時点で終了する |
| コスト上限 | 設けない |
| 通知 | run の合格と 20 iter 未達を Grok Bot 専用通知経路で作成者に通知する |
| 監視 | Haiku が定期起動し、ログと指標から異常を検知する |
| 実行時入力 | 教師記事の本文と URL、対象リポジトリの owner/name は run 開始時に与える。本書では値を扱わない |

## 5. 入出力

### 5.1 実行時入力

| 入力 | 置き場所 | 備考 |
|---|---|---|
| 教師記事本文 | `teacher/article.md` | judge のみが読む |
| 教師記事 URL | 設定値 | 教師記事 URL 集合の元。generator のプロンプトには渡さず、除外項目とマスク項目の生成にのみ使う |
| 対象リポジトリ | ツール層の設定値（owner/name） | ツール入力からは受け付けない |
| ルーブリック | `teacher/rubric.yml` | 7.1 で抽出し作成者が確定する。run 中は変更しない |
| 初期環境 | `env/` の 3 ファイル | 初期版の作り方は【未決】（12 章 A-5） |

### 5.2 出力

| 出力 | 内容 |
|---|---|
| `jobs/run-NNNN/iter-MM/article.md` | その iter で生成した記事 |
| `jobs/run-NNNN/iter-MM/score.json` | 軸ごとの点数・根拠・不足特徴、合計と合格判定 |
| `jobs/run-NNNN/iter-MM/env_diff.md` | その iter で加えた環境差分 |
| 環境の git 履歴 | iter ごとのコミット。合格時点のコミットが成果物 |
| run の結果 | 合格、または失敗（20 iter 未達） |
| 通知 | run 終了の通知（7.5） |

## 6. システム構成

### 6.1 サービス一覧

| サービス | 役割 | モデル | 位置づけ |
|---|---|---|---|
| orchestrator | run と iter の進行管理。LLM を使わない | なし | 確定 |
| generator | 環境を読み、対象プロジェクトを調べ、全体解説記事を生成する | Claude Opus | 確定 |
| judge | 生成記事を教師記事とルーブリックで採点する | Claude Opus | 確定 |
| refiner | judge の結果を元に環境を書き換える | Claude Fable | 確定 |
| monitor | 定期起動でログと指標を読み、異常を検知して `jobs/` 配下に記録する | Claude Haiku | 確定。記録の置き場所と形式は【提案】（7.6、12 章 B-5） |
| notifier | run 終了通知を Grok Bot 専用通知経路へ配送する | なし | 【提案】配送を独立サービスにし、通知文の生成に LLM を使わないこと（12 章 B-5）。通知そのものは確定 |
| 通知先 | 作成者が用意する Grok Bot 専用 webhook | 基盤外 | 確定。webhook の用意は本基盤の範囲外 |

モデルの割当は初版のとおり維持する。モデル ID、SDK、API の呼び出し方（provider 側ツールの利用を含む）は実装時に決める【提案】（12 章 B-6）。

### 6.2 アクセス境界

各サービスは Docker コンテナとして分離し、必要最小限のマウントとネットワークだけを与える。表の「外向き通信の宛先」は各サービスが到達してよい宛先の定義であり、宛先単位の強制を何で実現するかは 8.3 で扱う。

| サービス | マウント | 外向き通信の宛先 | 秘密 |
|---|---|---|---|
| orchestrator | jobs 読み書き | なし | なし |
| generator | env 読み取り、jobs 書き込み | Anthropic、GitHub。web 検索の宛先は 8.1.4 の方式に依る | Anthropic API キー、GitHub PAT |
| judge | teacher 読み取り、jobs 読み書き | Anthropic | Anthropic API キー |
| refiner | env 読み書き、jobs 読み取り | Anthropic | Anthropic API キー |
| monitor | jobs 読み取り、env の git log 読み取り。jobs への書き込みは異常記録の領域（【提案】`jobs/alerts/`）のみ | Anthropic | Anthropic API キー |
| notifier【提案】 | jobs の通知用領域 読み書き | Grok Bot 専用通知経路のホスト 1 つ | webhook URL。認証情報が必要な場合はそれも（要否と形式は 12 章 C-2） |

- generator と refiner は教師記事を読めない。judge と refiner は情報源（GitHub）と web に出られない。
- xAI API の宛先と `XAI_API_KEY` は構成に含めない。初版 5.2 の monitor 行から削除する。
- 秘密の渡し方は【提案】環境変数ではなくファイルマウント（12 章 B-4）。

## 7. 機能要件

### 7.1 ルーブリック抽出（初回のみ）

- Fable が教師記事を読み、採点軸と各軸の 0〜4 点の状態定義を `teacher/rubric.yml` に書き出す。
- 作成者がレビューし、確定する。確定後は run の途中で変更しない。
- 軸の定義は、確定後は教師記事を参照しなくても採点できる記述（数値、型）に寄せる。
- 生成記事は教師記事と同じプロジェクトを解説するため、内容が似ることは意図どおりである。【提案】軸は文体・構成の特徴に限り、内容の一致そのものを得点にしない（12 章 B-1）。

採点軸の候補:

| 軸 | 0 点 | 4 点 |
|---|---|---|
| 記事の骨格 | 導入なしで本題に入る | 教師記事と同じ順序で進む |
| 見出しの粒度 | 階層が単一、または乱立 | 教師記事と同じ階層と数の範囲 |
| 語尾と人称 | 文体が混在 | 教師記事と一致 |
| 一文の長さ | 平均が教師記事から大きく離れる | 平均と分散が教師記事の範囲内 |
| コードブロック | なし、または説明なし | 教師記事と同じ頻度で前後に説明がある |
| 情報源の示し方 | 出典なし | Issue や ADR へのリンクの置き方が同じ |
| 冒頭と結び | 定型なし | 教師記事と同じ型の導入とまとめがある |

### 7.2 チューニングループ

1. orchestrator が `jobs/run-NNNN/iter-MM/` を作り、generator を起動する。
2. generator は `env/` と題材指示（一文）を読み、GitHub ツールと web 検索で対象プロジェクトを調べ、記事をゼロから書いて `article.md` を置く。前 iter の記事は入力にしない。
3. judge は `article.md`、`teacher/article.md`、`teacher/rubric.yml` を読み、`score.json` を置く。
4. 合計が 80% 以上なら run を合格として終了する。その iter では環境修正を行わない。合格を通知する（7.5）。
5. 未満なら refiner が `score.json` と `env/` を読み、環境を書き換えて commit する。次の iter へ進む。
6. 20 iter 目で 80% 未満なら run を失敗として閉じ、20 iter 未達を通知する（7.5）。21 iter 目のディレクトリは作らない。

`score.json` の内容:

- 軸ごとの点数
- 軸ごとの根拠（生成記事からの引用）
- 軸ごとの不足している特徴
- 合計と合格判定

本書で確定しない事項:

- 20 iter 未達で閉じた後に自動で次の run を始めるかは【未決】。本書は「失敗として閉じ、通知する」までを確定とする。【提案】自動再開はせず、次の run は作成者の手動操作で始める（12 章 A-1）。
- API 障害やタイムアウトで採点に至らなかった iter の扱い。【提案】20 とは別の失敗予算で数え、連続または累計の上限に達したら run を中断し、`jobs/` に記録する（12 章 B-2。採否と上限値はそこで決める）。中断を外部通知するかは、通知事象を増やす論点として 12 章 A-2 で決める。本提案だけでは通知事象（7.5 の 2 つ）を増やさない。
- 合格点の端数（満点 × 0.8 の切り上げか切り捨てか）と軸の重みは、ルーブリック確定時（12 章 A-4）に併せて決める。重みを設ける場合も、合格判定は重み付け後の合計が 80% 以上であることのみとし、ほかの合格条件は設けない。

【提案】refiner への入力は、全 iter の score 推移と直近数 iter の `env_diff.md` とし、同じ修正の往復を避けることを refiner の責務にする（12 章 B-1）。

### 7.3 題材指示

- generator に与える題材指示は「対象プロジェクト全体の解説記事を書く」の一文で固定する。run 内のすべての iter で同一である。
- 参照すべき README、ADR、Issue の一覧は作成者が入力しない。何を読むかは generator が `env/` に従って決める。したがって情報収集の仕方も環境のチューニング対象に含まれる。
- Issue、ADR、ドキュメントは対象プロジェクトを調べるための資料であり、Issue ごと・ADR ごとの記事は作らない。

### 7.4 generator のツール

GitHub REST API を内部で呼ぶ読み取り専用のツール層を generator に置く。

| ツール | 入力 | 出力 |
|---|---|---|
| search | query | 種別、タイトル、URL、冒頭 200 字の一覧 |
| get_issue | number | タイトル、本文、ラベル、作成日、コメント一覧 |
| list_files | path | ファイル一覧 |
| read_file | path | ファイル本文 |

確定事項:

- 認証は権限なしの PAT を generator にだけ渡す。未認証のレート制限を避けるため。judge、refiner、monitor には渡さない。
- ツール層は読み取り専用とし、書き込み系の HTTP メソッドを実装しない。
- 対象リポジトリの owner/name はツール層の設定値で固定し、ツール入力からは受け付けない。search には対象リポジトリの限定をツール層が付与し、他リポジトリの内容を返さない。
- 応答に含まれる URL のうち、教師記事 URL 集合に一致するものはマスクする（8.1）。他の URL（同じ Zenn アカウントの他記事を含む）はマスクしない。

【提案】（12 章 B-3）:

- レート制限ヘッダを読み、残量ゼロまたは 403 / 429 では待ってから再試行する。同時接続は 1 とする。
- 1 iter あたりの GitHub 呼び出し回数と read_file のサイズに上限を置き、超えたらツールがエラーを返す。LLM のループで 1 iter が長引くことを防ぐ目的。
- Issues API は PR も返すため、PR は種別を明示するか除外する。
- 宛先は GitHub REST API のホストのみとし、web UI や raw 配信ホストには出ない。リダイレクトは追従しない。
- commits API（git 履歴）は読まない。情報源（Issue、ドキュメント、ADR）に不要であり、過去の下書きが露出する面を増やさないため。

### 7.5 通知

確定事項:

- 通知先は Grok Bot 専用通知経路である。作成者が本基盤専用の Grok Bot webhook を用意し、基盤はその webhook へ一方向に POST する。別プロジェクトの通知先は流用しない。
- 通知する事象は run の合格と 20 iter 未達の 2 つ。1 run につき終端通知を 1 件だけ生成し、送信を試みる。合格と失敗の両方を生成することはない。到達と表示は保証せず、送信結果を記録する。
- xAI API は使わない。
- webhook の用意、webhook URL の取得、認証情報が必要な場合はその取得（要否と形式は 12 章 C-2）、疎通確認は本書の範囲外であり、実装・連携時に作成者が行う。

【提案】配送方式（12 章 B-5）:

- 通知文の生成に LLM を使わない。notifier は固定スキーマを機械的に組み立てる。
- run の合格・失敗は orchestrator が決定的に判定し（iter 番号と score 合計）、monitor の起動間隔に依存しない。
- orchestrator は `jobs/outbox/` に通知レコードを書き、notifier（LLM なし、別コンテナ）が読んで POST する。orchestrator 自身は外向き通信を持たない。
- run の結果は `score.json` と run の状態ファイルに先に書かれ、通知の成否は run の進行に影響しない。ローカル記録は通知経路の稼働状態に関係なく常に残す。
- 送る内容は固定スキーマのみとし、自由記述フィールドを持たない。項目は事象種別（合格 / 失敗）、run 番号、iter 数、合格基準、最良 iter の合計と満点、合計の推移、環境のコミットハッシュ、開始・終了時刻、基盤インスタンス ID。
- 送らないもの: 教師記事の本文と URL、生成記事の全文・抜粋、`score.json` の根拠と不足特徴、環境の本文と差分、API キー、PAT、webhook URL、webhook の認証情報、ホスト名、対象リポジトリの owner/name。
- 同一事象の重複送信は冪等キーで抑止する。送信失敗は指数バックオフで再送し、上限で失敗として記録する。4xx は設定不備とみなし再送しない。再送回数と間隔は提案値であり実装前に決める。
- 基盤が記録する「送信済み」は受信側が成功応答を返したことを意味し、チャットへの表示は保証しない。表示の確認は連携時に手動で行う。
- notifier は応答の HTTP ステータスのみを扱い、応答本文を読まず、保存せず、LLM に渡さない。

【未検証】（12 章 C-2）: webhook の実ホスト名、認証情報の要否と送り方、成功ステータス、payload サイズ上限、受信側の重複抑止の有無。

【未決】（12 章 A-2）: 7.6 の残りの異常、手動停止の受理、失敗予算による中断（7.2 の【提案】を採る場合）を同じ経路で通知するか。採るまで通知事象は上の 2 つのみ。

### 7.6 監視

monitor は cron で定期起動し、以下を異常として検知する。

- 反復上限に達した run の失敗
- スコアが 5 iter 連続で上がらない
- 同じ環境差分の繰り返し
- API エラーの連続
- 1 iter が一定時間を超えて終わらない

初版の「異常を Grok に報告する」は、xAI API の廃止に伴い次のとおり改める。

- 検知した異常は `jobs/` 配下に記録する（確定）。初版の「報告する」から外部経路（xAI API）を除いた最小の置き換えであり、3.1 と 6.1 の「異常の記録」はこれを指す。記録は通知経路を経由しないため、通知経路の稼働状態に関係なく残る。
- 記録の置き場所を `jobs/alerts/` とすることと、記録の形式は【提案】（12 章 B-5）。採否に関わらず、記録すること自体は上の確定に従う。
- 反復上限に達した run の失敗は 7.5 の通知として作成者に届ける。検知主体は【提案】orchestrator（決定的判定）。monitor はその記録を確認する側に回る。
- 残り 4 種を外部通知するかと、その経路は【未決】（12 章 A-2）。決まるまでは記録のみを行う。
- monitor の起動間隔と「1 iter の一定時間」の閾値は【未決】（12 章 A-6）。iter の所要時間が分かってから決める。

## 8. 非機能要件

### 8.1 教師データの隔離

#### 8.1.1 基盤が保証する境界（確定）

- generator と refiner は `teacher/` をマウントしない。
- judge のフィードバック（`score.json`）は軸、点数、不足している特徴のみとし、教師記事の文を引用しない。
- generator の web 検索と取得から教師記事 URL 集合を除外する。`zenn.dev` 全体や作成者アカウント全体は除外しない。初版 7.1 の「作成者の Zenn アカウント配下を除外する」はこれに置き換える。
- 対象リポジトリ内に教師記事への URL がある場合、ツール層でマスクする。マスク対象も教師記事 URL 集合のみとする。
- 以上の目的は「基盤が教師本文を generator と refiner に渡さない、取りに行かせない」ことの保証である。8.2 の版管理と 8.3 の分離はこの目的に従う。

#### 8.1.2 教師記事 URL 集合

除外とマスクの対象を次で定義する。

1. 正規 URL: 実行時入力の教師記事 URL を正規化したもの。スキーム除去、ホストの小文字化、`www.` 除去、末尾スラッシュ除去、クエリとフラグメントの除去。
2. 自明な変種: 1 に対するスキーム違い、`www.` 付き、末尾スラッシュ付き、クエリまたはフラグメント付き。
3. 記事固有の別名 URL（任意）: 同じ本文を返すことが確認された、記事の slug を含む URL。存在と形式は【未検証】（12 章 C-3）。
4. 過去 URL（任意）: 教師記事が slug やアカウント名の変更を経ている場合の旧 URL。作成者が把握している範囲で与える。

2 の変種は、除外項目として個別に列挙するのではなく、正規 URL をパス付き項目として 1 つ入れ、その前方一致（F-3）で覆う。パス付き項目には `?` と `#` を含められない（F-8）ため、クエリ付き・フラグメント付きの変種を項目として書くことはできない。前方一致で実際に覆われるかは【未検証】（12 章 C-3）。ツール層のマスクと事後検知は正規化（1）の後に比較するため、変種の扱いに差は出ない。

含めないもの（確定）: 同じアカウントの他の記事、`zenn.dev` の他のページ、第三者の転載・引用ページ、アカウント単位の資源（フィード、アカウントの記事一覧ページ等）。アカウント単位の資源を含めないのは「除外は教師記事だけで、アカウント全体は除外しない」という確定に従う。フィード等を経由して教師記事の一部が届く可能性は 8.1.3 の保証範囲外として扱う。

【提案】この集合は web 検索の除外項目、ツール層のマスク、事後検知の照合の 3 箇所で同じ定義を使い、1 つの正規化関数と 1 つの設定値から導く（12 章 B-7）。

#### 8.1.3 保証範囲

基盤が担うもの（確定）:

- `teacher/` のマウント境界（8.1.1）。
- ツール層による教師記事 URL 集合のマスク。
- generator の web 検索リクエスト全件に除外を付けること。除外が付けられない場合は送らない（fail-closed）。8.1.1 の「web 検索から除外する」は全リクエストに付いて初めて成立するため、確定の帰結である。

基盤が担うものに加えることを【提案】している事項:

- generator の直接の外向き通信を許可宛先以外は既定で拒否すること。実現手段は 8.3 の egress proxy（12 章 B-4）であり、採否が決まるまで「基盤が担うもの」には含めない。

基盤の保証範囲外として扱うもの。「起きない」とは主張せず、要件として対策を約束しない。

- 第三者が教師記事を転載・引用したページが、web 検索結果や対象リポジトリの Issue コメント経由で generator に届くこと。
- 同じ Zenn アカウントの他記事が教師記事を引用・要約している場合に、その一節が届くこと。これは「教師記事のみ除外」の決定に伴って受け入れる。
- アカウント単位の資源（フィード、記事一覧ページ等）を経由して、教師記事の題名、要約、URL の一部が届くこと。これも「アカウント全体は除外しない」の決定に伴って受け入れる。
- 対象リポジトリ内に教師記事の本文や下書きが置かれている場合に、ツール層がそれを情報源として返すこと。有無は実行時に確認する（12 章 C-1）。
- モデルの学習データに教師記事が含まれている可能性。
- 検索プロバイダ側の URL 照合の細部（8.1.4）。

【提案】保証範囲外の経路は事後検知で扱う（12 章 B-7）。generator のツール入出力（検索結果の URL と題名、GitHub ツールの戻り）を `jobs/run-NNNN/iter-MM/tool_io/` に記録し、教師本文を読める側に置く leak_checker（LLM なし）が iter 完了後に照合する。一致があれば「教師接触あり」として記録する。これは検知であって予防ではない。接触ありの iter を無効にするか記録のみとするかは【未決】（12 章 A-3）。

#### 8.1.4 除外の実現方式（実装前に選ぶ）

除外方式は作成者が未選択であり【未決】（12 章 A-7）。ここでは公式仕様で確認できた事実と、方式ごとの保証範囲を示す。どの方式でも 8.1.1 の境界と 8.1.3 の「基盤が担うもの（確定）」は満たさなければならない。

公式仕様で確認できた事実（Anthropic Claude Platform ドキュメント、2026-11-06 取得）:

| # | 事実 | 出典 |
|---|---|---|
| F-1 | `web_search` ツールの `allowed_domains` と `blocked_domains` はどちらか一方のみ指定できる。両方送ると 400 | https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool#domain-filtering |
| F-2 | 項目はスキームなしの素のドメインに、任意でパスを付けた形（例: `example.com/blog`） | 同上 |
| F-3 | パス付き項目は web search で有効で、「そのパスの後ろに続くものすべて」に一致する。つまり前方一致であり、URL の完全一致指定ではない | https://platform.claude.com/docs/en/agents-and-tools/tool-use/server-tools#domain-filtering |
| F-4 | `web_fetch` はドメインのみで一致し、パス付き項目は web fetch の URL に一致しない。provider 側 web fetch に記事単位の除外は存在しない | 同上 |
| F-5 | サブドメインは自動的に含まれる。ワイルドカードはパス部のみ可 | 同上 |
| F-6 | 検索プロバイダはパス接尾辞をホスト規則ほど厳密ではない URL パターンとして照合する、と公式が注意している。なお同ページにある「各リストは 1〜64 項目」の上限は Managed Agents の toolset についての記述であり、同ページ自身がこれを Messages API のツールとの相違点として挙げている。Messages API 側の項目数上限は本書では断定しない（12 章 B-6 の方式に依る。確認は C-3） | https://platform.claude.com/docs/en/managed-agents/tools-web-restrictions#path-suffixes-on-web-search-domains |
| F-7 | 検索結果の本文は暗号化されて返り、クライアントは本文を検査できない。受信後に見えるのは URL と題名 | https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool#search-results |
| F-8 | `web_search` のパス接尾辞には空白、`?`、`#`、および `$`、`,`、縦線（パイプ）、`^`、`!` を含められない。項目末尾の `/` 1 個は無視される。同ページは「`web_search` でも素のホスト名を優先せよ」とも述べている。いずれも Managed Agents 側のページの記述であり、Messages API に同じ制約が当てはまるかは C-3 で確認する | https://platform.claude.com/docs/en/managed-agents/tools-web-restrictions#domain-format 、同 #path-suffixes-on-web-search-domains |

方式の候補（すべて【提案】）:

| 方式 | 概要 | 除外の保証主体 | 新規の宛先・秘密 | 受入試験で基盤側が確認できること | 留意点 |
|---|---|---|---|---|---|
| A | provider 側 `web_search` の `blocked_domains` に教師記事 URL 集合をパス付き項目で入れる。provider 側 `web_fetch` は使わない。受信後に URL を監査する | Anthropic と検索プロバイダ | なし | 全リクエストに項目が付いていること。返った URL に集合が含まれないこと | 前方一致の細部は【未検証】（F-3、F-6）。本文の取得機能は持たない（F-4） |
| B | 検索と取得をクライアント側ツールとして基盤に置き、外部検索 API の結果 URL を教師記事 URL 集合と照合してからモデルに渡す。取得はリダイレクトを 1 ホップずつ照合し、最終 URL と canonical も照合する | 基盤自身 | 外部検索 API の宛先と秘密。取得仲介には広い外向き通信が要る | URL 照合の挙動を完全一致の単位で検証できる | 取得仲介の外向き通信方針が 8.3 の【提案】既定拒否と衝突するため別途決める。検索 API の選定が要る |
| C | 検索は A、取得は B の仲介 | 検索は Anthropic、取得は基盤 | 取得仲介の分のみ | B の取得部分と同じ | 本文取得が要る場合に B より変更が小さい |

方式に依らず満たすこと（確定事項の帰結。根拠を添える）:

- 全 web 検索リクエストに教師記事 URL 集合の除外を付ける。8.1.1 の除外は全リクエストに付いて初めて成立するため。
- provider 側 `web_fetch` はどの方式でも有効にしない。記事単位の除外ができない（F-4）ため、8.1.1 の「取得から除外する」を満たせないため。
- 送信したツール定義または仲介の照合ログを iter ごとに記録し、受入試験（AC-10）で全件に除外が含まれることを確認できるようにする。記録がなければ「全リクエストに除外が付いた」ことを事後に示せず、上の 1 点目が満たされたと確認できないため。記録の形は方式に依る。

方式に依らず満たすことに加える【提案】（12 章 B-7）:

- generator の API 呼び出しは 1 箇所に集約し、送信直前に除外項目の存在を検証する。無ければ送らない。上の fail-closed を実装で確実にするための構造案である。

【提案】（12 章 A-7 の判断材料）: 本文取得が不要なら方式 A を既定とする。変更が最小で、新規の宛先と秘密がない。除外の挙動を基盤側で検証できることを要件に含めたい場合、または本文取得が要る場合は B または C。

### 8.2 再現性（版管理）

確定事項:

- 環境は iter ごとに git commit し、`score.json` と 1:1 で対応づける。
- `jobs/` は run と iter の単位で残し、削除しない。
- ルーブリックは確定後、run の途中で変更しない。

【提案】（12 章 B-4）:

- `env/` を独立した git リポジトリにし、refiner にはその `.git` だけを見せる。目的は、教師本文がプラットフォームリポジトリの git オブジェクト経由で generator や refiner から読める経路を塞ぐこと（8.1.1 の境界の維持）。
- `teacher/` はプラットフォームリポジトリにコミットしない。リポジトリは public であり、generator は GitHub の読み取り権を持つため。
- コミットメッセージに run 番号、iter 番号、score 合計を含め、合格した run の環境にタグを打つ。

### 8.3 分離

確定事項:

- 各サービスは別コンテナで動かし、6.2 の境界を与える。
- サービス間の通信は共有ボリューム経由とし、サービス間 HTTP は設けない。

事実: Docker compose の internal ネットワークは「外に出られる / 出られない」の二値であり、「Anthropic と GitHub のみ」のような宛先単位の制限はできない。初版 7.3 の「5.2 の境界を compose で強制する」は宛先限定については成立しない。宛先限定を何で実現するかは【提案】の採否による。採用しない場合、6.2 の宛先は定義に留まり、基盤は宛先単位の強制を行わない。

【提案】（12 章 B-4）:

- 宛先の限定は allowlist を持つ egress proxy コンテナで行う。各役割コンテナは internal ネットワークのみに属し、外へ出る経路は proxy だけにする。proxy は TLS を終端せず、宛先ホスト名で判定する。
- 未知の宛先、IP リテラル、私設アドレスとリンクローカルへの接続は拒否する（8.1.3 の「既定で拒否」はこれを指す）。
- どのコンテナにも Docker socket を渡さない。orchestrator の「起動する」は、常駐サービスが状態ファイルを見て自分の番を進める方式で実現する。
- 役割ごとに非 root の uid を分け、過去 iter への generator の書き込みと、refiner からの `article.md` 読み取りをパーミッションで禁じる。
- `teacher/`、`env/`、`jobs/` を独立したボリュームにする。
- proxy は URL パスを見ないため、対象リポジトリの固定（7.4）はツール層の責務とする。

【未決】実行環境（12 章 A-8）。internal ネットワークの実装はホストに依存するため、8.3 の受入試験は実行ホスト上で行い結果を記録する。

### 8.4 受信境界

【提案】（12 章 B-5）:

- 基盤は待ち受けポートを公開せず、コンテナ内にも listener を置かない。webhook は基盤から Grok Bot への一方向である。
- 停止・再開・やり直しの指示は `jobs/control/` のローカル制御ファイルでのみ受け付ける。Grok Bot のチャットから基盤を操作する経路は設けない。
- 秘密（webhook URL、webhook の認証情報がある場合はそれ、API キー、PAT）はログ、outbox、通知内容に書かない。

## 9. 停止・再開・失敗時挙動

初版に記載がなく、作成者の確定もない。以下はすべて【提案】（12 章 B-2）。

- `jobs/run-NNNN/state.json` を唯一の進行状態とし、iter 内の各ステップ完了をマーカーファイルで表す。書き込みは一時ファイルからの rename で行う。
- run の状態は `running`、`paused`、`passed`、`failed` を基本とし、失敗予算や再開拒否を採る場合にだけ `aborted`、`needs_human` を加える。`aborted` と `needs_human` はローカル記録上の状態であり、これらを外部通知するかは 12 章 A-2 に従う。
- クラッシュ後は同じ iter 番号の未完了ステップから再開し、完了済みステップは再実行しない。
- 再開時は状態ファイルの環境コミットと `env/` の HEAD を照合し、不一致なら拒否する。
- 1 つの環境リポジトリに対して同時に進む run は 1 つ。
- 再試行で直らない API エラー（認証エラー等）は run を `paused` にして記録する。
- 通知先に到達できなくても run の結果とローカル記録は失わない。
